# 比較表: 本編 Three.js 仙台 vs 本試作 Cesium+PLATEAU 仙台

作成: 2026-11-22。証拠は `../README.md` の各検証節と `../captures/*.json` の実測値。
本編側の数値・事実は Earth Studio 調査報告書 §1（実コード読解に基づく）由来として明記する。
最終判断は Shibu の実機比較に委ねる。

## 採否基準 (Shibu 明言、2026-11-22) と実機成績

> 「スクロールで移動して動くサイトというのが大前提なので、重すぎると無理」

- 実データ方式の合否は実在感ではなく **iPhone 実機でスクロールに追随して滑らかに動くこと** で決まる。評価の筆頭は「静定した画質」ではなく「動きながらの追随」である。
- **タイル方式 (Cesium3DTileset) の iPhone 実機成績は2回不合格** (詳細は README「実機所見2件目と第2段対策」節):
  1. 素の構成 (SSE 16 + DEM): 繰り返しクラッシュで表示不能 (2026-11-22 21:53)
  2. 第1段軽量プロファイル (SSE 32 等): 「重すぎる」で実用不可 (同 22:08)
- 第2段 (GLB 方式をモバイル既定化) は公開・実機確認の前提作業 (GLB のリポジトリ配置) が未完了で、**実機未検証**。

## スクロール追随の実測 (VM、measure-scroll.mjs、mobile プロファイル、p 0→1 一定速度スイープ)

| 項目 | タイル方式 (SSE 48) | GLB 方式 (24枚) |
|---|---|---|
| スイープ中の追加転送 | **+42.6MB / 119 req** (移動中も流れ続ける) | **+0.58MB / 31 req** (オルソのみ。建物はゼロ) |
| 停止後に静定するまで | **180 秒でも到達せず** (間に +96.8MB) | **0.1 秒** |
| 総転送量 | 151.3MB (未静定のまま終了) | 86.9MB (完了。うち GLB 78.7MB は初期に固定) |

fps は SwiftShader では両方式とも 1〜2fps で実機の代理にならない (比較に使わない)。
構造の差は明確で、タイル方式は「動くほど読み込みが増え、止まっても追いつかない」。
GLB 方式は初期コストと引き換えに、読み切り後の追随に追加転送が要らない。
静定手順での比較 (measure-stage2.mjs) でも、タイル方式は SSE 48 で建物 112.8MB・
静定未到達、GLB 方式は総量 99.3MB で静定到達 (24/24 読込) だった。

## 転送量の実測まとめ（本試作、CDP 実測・VM SwiftShader＋プロキシ経由）

ホスト別内訳が取れているセッション（terrain / terrain2 検証、6セッション）:

| 内訳 | 実測範囲 | 備考 |
|---|---|---|
| PLATEAU 建物 (3D Tiles) | **234.05〜284.92MB** / 76〜97 req | 全体の約85〜90%を占める支配項 |
| オルソ (PLATEAU-Ortho) | 0.02〜30.34MB / 38〜212 req | 未静定セッションでは小さく出る（流れ切っていない） |
| DEM (GSI 標高タイル) | 0〜9.08MB / 75〜125 req | terrain=dem のセッションのみ |
| その他 (Cesium 本体＋ページ資産、ローカル配信) | 6.76MB / 16〜17 req | 全セッションほぼ一定 |
| **セッション総量** | **249.63〜314.39MB** | 同6セッション。heightfix セッションは 367.66 / 444.86MB、grade セッションは 266.20〜271.37MB、verify ステージは 262.75〜309.31MB |

個別の小さい実測:
- p=0 付近の表示のみ（プロキシキャッシュ蓄積分）: 44ファイル超・約14MB（うち tileset.json は 141,840B）
- オルソのみ（地表修正の確定セッション）: 200応答 40枚 / 7,208,622B（約7.2MB）
- Model 経路（GLB 24枚の回廊先読み）: 78,664,599B（約78.7MB）— tileset 方式の同区間より大きい

**注意（読み違い防止）**: 上記のセッション総量は、VM の SwiftShader で複数 p を往復し
静定まで数分待った「検証セッション」の値であり、一般ユーザーの1回の通しスクロールと
同一ではない。ただし内訳が示す構造（建物タイルが支配的で、p=0 の静止画だけでも
約14MB、回廊全体に触れれば百MB級）は条件が変わっても桁は変わらないと見られる。

**追記（2026-11-22 第2段）**: 「p を 0→1 へ一定速度で1回通し」相当の条件は、
採否基準（スクロール追随）の確定を受けて measure-scroll.mjs で実測した
（結果は冒頭「スクロール追随の実測」節。モバイルプロファイル、tileset SSE 48 と
GLB 方式の比較）。「p=0 静止のまま静定まで」は引き続き未実測で、実機または
実GPU環境での計測項目として残す。なお本編ユーザーの1回通しの厳密な転送量は、
タイル方式では静定条件の置き方で変わるため単一値では示せない（追随計測では
未静定のまま 151.3MB に達した）。

## 比較表

| 項目 | 本編 Three.js 仙台 | 本試作 Cesium+PLATEAU 仙台 |
|---|---|---|
| 初期読み込み量 | **約944KB**（単一バンドル、外部ファイル読み込みなし。報告書§1の事実） | p=0 付近の表示だけで **約14MB**（実測）。加えて Cesium 本体等の資産 約6.76MB/セッション（実測）。初期表示の桁が約15倍以上違う |
| 通しでの総転送量 | バンドル約944KB で完結し、追加転送は発生しない（構造上の事実） | 検証セッション総量 **250〜445MB**（実測、条件は上記注意書き）。支配項は PLATEAU 建物 234〜285MB。一般ユーザーの1回通しの厳密値は**未実測**だが、百MB級は避けられない構造 |
| 実在感（建物形状・テクスチャ・看板） | 箱＋窓明かりのプロシージャル表現。実在の建物形状・看板・質感は再現できない（報告書§1-6の事実） | **実在の建物形状とテクスチャ**（仙台駅の屋根形状・ファサードが実物どおり。fixed-tileset-p0.png 等で確認）。ただし静定後も前景に白い無テクスチャ箱が残る区域があり（原因は LOD 選択か LOD1 のみ収録か**未切り分け**）、看板の判読可否は**未検証** |

| 夜・夕の演出 | 夕方→完全な夜へ進行する演出がコンセプトとして成立し、Shibu が「完全な夜」を受理済み（報告書§2-4ほか） | 標準機能では明るさの軸は再現できる（平均輝度 p0: day 95.7 → dusk 63.6 → night 11.7、実測）。ただし 17:20 JST では太陽高度 +13° で空は青いまま（夕景の空には日没前後の時刻設定が前提）。night は「灯りのない暗い街」止まりで、窓明かり点群の試作は建物に整合せず本採用不可 — **夜景の核（灯り）は建物整合の重ね物が別途必要**。フィナーレでは広瀬川が水面として識別不可 |

## 暫定結論（証拠付き・断定ではない）

現時点の証拠から言える、都市ごと・ショットごとの使い分けの暫定像:

1. **俯瞰の実在感は実データ優位（暫定）**: p=0 の仙台駅周辺では、実在の建物形状・
   テクスチャが本編のプロシージャル表現では原理的に出せない情報量を持つ
   （fixed-tileset-p0.png）。都市紹介的な俯瞰ショットでは実データが強い。
2. **夜のフィナーレは本編優位（暫定）**: 本試作の night は「灯りのない暗い街」で、
   広瀬川も水面として読めない。本編は夕方→完全な夜の演出と灯りのある夜景が
   成立している。実データで並ぶには建物整合の発光レイヤという別工程が要る。
3. **街路レベルは条件付きで実データが戦える（暫定）**: 高度補正と DEM 地形で
   構図は成立したが、白箱・建物内キーの問題が残り、最終画質は実機未検証。
   本編は街路の演出（アーケード、祭りの要素）まで含めて実機実績がある。
4. **転送量は実データの構造的な弱点（確定に近い）**: 初期 約14MB vs 944KB、
   通し百MB級 vs 追加転送なし。この差は最適化では桁が変わらない見込みで、
   モバイルデータ容量に制限のある利用環境では方式判断の最重要項目のひとつ。
5. **対称性は本編優位（暫定）**: 構図は両者とも決定論的だが、精細度まで含めた
   「同じ p = 同じ絵」はタイル方式では成立しないことが実測された。

これらは VM（SwiftShader）での検証に基づく暫定であり、**最終判断は Shibu が
iPhone 実機で両者を同条件で比較して行う**。特に実機性能・実回線での転送量と
追随・実GPUでの最終画質が未検証のまま残っており、それらが揃うまでは
どのショットについても方式を確定しない。

## 採否基準に照らした結論方向（2026-11-22 追記、証拠付き。最終判断は Shibu）

採否基準が「実在感」ではなく「スクロール追随の滑らかさ」と確定したことで、
上記の暫定結論の重み付けは次のように変わる:

1. **タイル方式は仙台のスクロール本編には不採用が妥当**: 実機2回不合格に加え、
   VM 追随計測でも構造的に追随不能（移動中も転送継続、停止後180秒でも未静定）。
   俯瞰の実在感（暫定結論1）の優位は、この基準の下では本編採用の根拠にならない。
2. **GLB 方式は「条件付きで存続」**: 追随の構造条件は満たすが、初期 78.7MB の
   読み込みと全ジオメトリ常駐での実機 fps・メモリが未検証。**GLB 方式でも
   iPhone 実機で滑らかさが確認できない場合は、実データ方式は仙台のスクロール
   本編には不採用が妥当** と結論づける。
3. 実データ方式が不採用となった場合に残る使い道は、スクロール本編ではなく
   「止まって見せる」用途（俯瞰の静止画・都市紹介ショット等）に限られる。
   その場合も夜のフィナーレは本編優位（暫定結論2）のままである。
